So now we are familiar with states, we know that React makes changes on DOM based on the state changes.

To manage the states in components, we can use hooks like use states, use reducers.

use state is for when we want to store a value in our component.
use reducer is for the times that managing states is harder and we have multiple states.
We use it to reduce code repeats and complexity.

In react we can share states between components. 
If we want the states to be used in multiple components, we needed to put it in the upper layer.
Which was not efficient due to the matter **prop drilling** that could affect the performance.

So we use contexts. It can manage the states between components when contains them as provider.
But even context has some limits.
1. Context is for small projects or not very complex.(you can use it otherwise, but you need more contexts).
2. Most common uses of context: Theming, user auth, localization(multi language), app settings

Why we say context are not good for complex situations?
It doesn't have a base structure and you can use many hooks in it.
When your project grows, you may have to use other contexts as well, which results in creating many providers, which can result in using a lot of nested provider elements from the context in main code(Scary, isn't it?)

So debugging and managing them can be difficult.

The other bad thing about context api is it's performance.
When using multiple components inside a provider wrapper, then one state changes and now every consumers of the provider get re-rendered.

It's not good for many change occurences during the use of the web.
